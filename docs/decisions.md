# Architecture Decision Records (ADR)

กติกา: ตัดสินใจเชิงสถาปัตยกรรมใหม่ทุกครั้ง → เพิ่ม ADR ที่นี่ก่อนเขียนโค้ด
รูปแบบ: บริบท → ตัดสินใจ → เหตุผล → เงื่อนไขที่จะทบทวน

## ADR-001: สถาปัตยกรรมเดียว สองโหมด (ไร้กล่อง + กล่อง Edge)
- **ตัดสินใจ:** ระบบกลางรับ NormalizedEvent โดยไม่สนแหล่งที่มา / โหมดไร้กล่องเป็นค่าเริ่มต้น / กล่อง Frigate เป็น upsell
- **เหตุผล:** ไร้กล่อง = friction ต่ำสุด ปิดดีลเร็ว ตรงวิสัยทัศน์ Plug & Play; กล่องแก้ปัญหากล้องเก่า/เน็ตห่วย/ฟีเจอร์พิเศษ และเป็นรายได้เพิ่ม
- **ทบทวนเมื่อ:** ไซต์ส่วนใหญ่กล้องเก่าเกินจนโหมดไร้กล้องขายไม่ได้จริง

## ADR-002: TypeScript ทั้งระบบ ไม่มี Python ใน MVP
- **เหตุผล:** งาน vision หนักอยู่ที่กล้อง/กล่อง ไม่ใช่คลาวด์; โค้ดเบสภาษาเดียวดูแลง่ายสำหรับทีมเล็ก; ผู้พัฒนาใช้ stack นี้คล่อง + AI coding tools ทำงานกับมันได้ดีที่สุด
- **ทบทวนเมื่อ:** มีลูกค้าต้องการวิเคราะห์วิดีโอต่อเนื่องฝั่งเซิร์ฟเวอร์ → เพิ่ม Python service เฉพาะงานนั้น (ไม่ rewrite)

## ADR-003: Supabase เป็นแกนกลาง (DB + Storage + Auth + คิว pgmq)
- **เหตุผล:** ผู้พัฒนาใช้อยู่แล้ว; เป็น Postgres แท้จึงมีประตูออก (dump ย้าย/self-host ได้); ลดจำนวนระบบที่ต้องดูแลเหลือน้อยที่สุด; ปริมาณ event ระดับสิบไซต์ Postgres ตัวเดียวเอาอยู่
- **ทบทวนเมื่อ:** บิลเกินหลักหมื่น/เดือน หรือ 30-50+ ไซต์ → พิจารณา self-host

## ADR-004: ไม่มี face recognition ใน v1
- **เหตุผล:** ข้อมูลชีวภาพภายใต้ PDPA ต้องขอ consent ยุ่งยากและเสี่ยงกฎหมาย; LPR/นับคน/ตรวจโซน ให้มูลค่าเกือบเท่ากันโดยติดแค่ป้ายแจ้ง CCTV ปกติ
- **ทบทวนเมื่อ:** มีลูกค้าต้องการจริงจัง + ปรึกษาทนาย PDPA แล้ว

## ADR-005: Fail-open — VLM ล่มต้องไม่ทำให้แจ้งเตือนเงียบ
- **ตัดสินใจ:** VLM timeout 20 วินาที → ส่ง alert ดิบ (ไม่มีคำบรรยาย) ทันที
- **เหตุผล:** พลาดเหตุจริงเสียหายกว่า alert ไม่สวย; ความเชื่อใจของลูกค้าคือ asset หลัก

## ADR-006: LINE เป็นช่องทางแจ้งเตือนหลัก
- **เหตุผล:** นิติ/รปภ.ไทยอยู่ใน LINE ไม่เปิดเว็บ; รองรับรูป + ปุ่มโต้ตอบ
- **ข้อระวัง:** LINE คิดเงินตาม push message → การกรอง alert หลอกด้วย VLM คือการประหยัดต้นทุนโดยตรง
- **ทบทวนเมื่อ:** ค่า LINE ต่อไซต์เกิน ~300 บาท/เดือน → พิจารณา digest/แอปแจ้งเตือนเอง

## ADR-007: เชื่อมไซต์ผ่าน Tailscale เท่านั้น ห้าม port forward
- **เหตุผล:** NVR เปิดพอร์ตสาธารณะโดนแฮ็กเร็วมาก และความเสียหายจะย้อนทำลายแบรนด์เรา; Tailscale outbound-only ทะลุ NAT เน็ตหมู่บ้านได้ ฟรีถึง 100 เครื่อง

## ADR-008: เก็บ raw payload ทุก event + feedback "แจ้งเท็จ" ตั้งแต่วันแรก
- **เหตุผล:** สองอย่างนี้คือสมบัติที่ลอกไม่ได้ — ใช้ debug, จูน prompt VLM, เทรนโมเดลอนาคต; เพิ่มทีหลังจะเสียข้อมูลช่วงแรกไปตลอดกาล

## ADR-009: กลยุทธ์ราคา "ถูกตอนเข้า แพงตอนโต"
- **ตัดสินใจ:** แพ็กเกจต่อโครงการ (ไม่ใช่ต่อกล้อง) เริ่ม ~1,990-5,990 บาท/เดือน + ค่าติดตั้ง; add-on และ segment พรีเมียม (โรงงาน/รปภ./multi-site เริ่ม 9,900+) เก็บมูลค่าภายหลัง; lock ราคา 12 เดือนในสัญญา
- **เหตุผล:** งบนิติจำกัด อนุมัติหลักพันง่าย; มูลค่าเก็บตอนลูกค้าสัมผัสของจริงแล้ว ไม่ใช่ตอนขอความเชื่อใจครั้งแรก

## ADR-010: Dashboard M4 — Auth แบบเราสร้างบัญชีให้, สิทธิ์ตาม profiles, กฎเก็บใน sites.rules
- **ตัดสินใจ (2026-08-09):**
  1. Supabase Auth แบบ email+password เท่านั้น **ไม่มีหน้าสมัครเอง** — เราสร้างบัญชีให้ลูกค้าตอน onboarding (B2B, ลดความงงของผู้ใช้ไม่เชี่ยวเทคโนโลยี และกันคนนอกสมัคร)
  2. สิทธิ์ผ่านตาราง `profiles`: role `admin` (ทีมเรา เห็นทุกโครงการ) / `site_user` (ลูกค้า เห็นเฉพาะโครงการตัวเอง) — โครงสร้างรองรับหลายโครงการตั้งแต่วันแรก
  3. การอ่านข้อมูลผ่าน RLS (client ใช้ session + anon key) / การเขียน (แจ้งเท็จ, บันทึกกฎ) ผ่าน server action ที่เช็ค session แล้วใช้ service key — ลดความซับซ้อนของ write policy
  4. กฎต่อโครงการเก็บเป็น jsonb ใน `sites.rules` (เปิด/ปิดแจ้งเตือนต่อประเภท, ช่วงเวลาเฝ้าเข้ม, ความไว AI) — **ยังไม่ถูกใช้จริงจนกว่า M2 (LINE)** ซึ่งเป็นผู้บริโภคกฎตัวแรก
  5. UI ยึดกติกา "คนไม่เชี่ยวชาญโปรแกรมต้องดูรู้เรื่อง": ภาษาไทยล้วน, สถานะเป็นสี (เขียว=ปกติ แดง=มีปัญหา), 3 หน้าหลักเท่านั้น (รวมโครงการ → เหตุการณ์ → ตั้งค่า)
  6. หน้า `/admin/<key>/events` แบบลิงก์ลับยังอยู่ชั่วคราวเป็นช่องทางสำรอง จะถอดเมื่อ dashboard ใช้แทนได้เต็มที่
- **เหตุผล:** นิติ/รปภ. ไม่ควรต้องเรียนรู้อะไรใหม่เกิน LINE + เว็บหน้าเดียว; แยกสิทธิ์ระดับแถวด้วย RLS ปลอดภัยกว่า filter ในโค้ด
- **ทบทวนเมื่อ:** ลูกค้าต้องการหลายผู้ใช้ต่อโครงการ/หลายโครงการต่อผู้ใช้ → เปลี่ยน profiles.site_id เป็นตาราง mapping

## ADR-011: Configuration as Data — กฎ 3 ชั้น + แม่แบบไซต์ + สวิตช์รายกล้อง
- **บริบท:** "กล้องแต่ละจุดควรดูอะไร" ต้องไม่ฝังในโค้ดหรือในหัวคนติดตั้ง มิฉะนั้นทุกไซต์คืองานฝีมือ scale ไม่ได้
- **ตัดสินใจ (2026-08-09):** ออกแบบเป็น 3 ชั้นซ้อนกัน
  1. **ชั้นกฎพื้นฐาน** — ทุกกล้องได้อัตโนมัติ ปิดไม่ได้ จึง**ฝังในโค้ด/prompt โดยเจตนา** (ไม่ใช่ config): กล้องออฟไลน์/ถูกบัง/ภาพมืดผิดปกติ, คนล้มไม่ลุก, ควัน/ไฟ, ชุลมุน/ทะเลาะวิวาท, รถชน — จุดที่ VLM ตอบได้โดยไม่ต้องเทรน
  2. **ชั้นโปรไฟล์ตามหน้าที่** — ตาราง `camera_profiles` (แถวข้อมูล ไม่ใช่โค้ด): ~6 โปรไฟล์ (ประตูเข้า-ออก, รั้ว/แนวเขต, พื้นที่ส่วนกลาง, ลานจอด, จุดทำงาน, ทางเข้าอาคาร/ทางหนีไฟ) แต่ละแถวเก็บ event ที่สนใจ + ระดับความร้ายแรง + บริบทเวลา + `vlm_prompt_th` — สร้าง/แก้โปรไฟล์ = แก้ข้อมูล ไม่ต้อง deploy
  3. **ชั้นคำสั่งภาษาคน** — `custom_instructions_th` ต่อกล้องและต่อไซต์ พิมพ์ไทยธรรมดา ถูกแนบเข้า prompt อัตโนมัติ = customize ระดับวัน (ไม้ตายที่คู่แข่ง rule-based ทำไม่ได้)
- **แม่แบบไซต์:** ตาราง `site_templates` (หมู่บ้านมาตรฐาน, คอนโด low-rise, คอนโด high-rise, ไซต์รปภ.) — playbook สะสมจากหน้างาน เปิดไซต์ใหม่ = เลือกแม่แบบ → จับคู่กล้องเข้าโปรไฟล์ → ปรับเฉพาะจุด
- **สวิตช์รายกล้อง:** `cameras.enabled` — ปิด = บันทึก event แต่ไม่วิเคราะห์/ไม่แจ้งเตือน (ราคาเริ่มต้นต่ำ ทุกกล้องที่ปิดคือ upsell ที่นอนรอ เปิดสวิตช์เดียวจบ)
- **หมายเหตุ:** face recognition เว้นช่องไว้ในดีไซน์แต่ไม่เปิดใช้ ตาม ADR-004 (PDPA)
- **ทบทวนเมื่อ:** โปรไฟล์เกิน ~15 ตัวหรือ template เริ่มมี logic ซับซ้อน → พิจารณา versioning ของโปรไฟล์

## ADR-012: Retention ตาม PDPA + Ops monitoring ขั้นต่ำ
- **ตัดสินใจ (2026-08-09):**
  1. **Retention:** event + รูป เก็บ 60 วันโดยปริยาย (ปรับต่อไซต์ได้ผ่าน `sites.rules.retention_days`) — worker กวาดลบอัตโนมัติทุก 6 ชม. สอดคล้อง PDPA (กำหนดอายุข้อมูล) และคุมค่า storage; ระบุอายุเก็บในสัญญาลูกค้าเสมอ ข้อยกเว้น: event ที่มี feedback (แจ้งเท็จ/เหตุจริง) เก็บถาวรเป็นข้อมูลจูนระบบ (ADR-008) โดยลบเฉพาะรูป
  2. **Dead-man switch:** worker เต้นชีพจรลงตาราง `system_status` ทุก 60 วิ — dashboard ฝั่ง admin ขึ้นแถบแดงถ้าชีพจรขาดเกิน 5 นาที (ตอบคำถาม "ใครเฝ้าคนเฝ้า")
  3. **Rotate siteKey:** ปุ่มในหน้าเชื่อมต่อ (admin) — สร้าง key ใหม่ทันที ของเก่าใช้ไม่ได้ ใช้เมื่อ key หลุดหรือถอนงานผู้รับเหมา
- **ทบทวนเมื่อ:** ลูกค้าต้องการ retention ต่างจากช่วง 30-180 วัน หรือระบบโตพอควรใช้ monitoring จริงจัง (Sentry/Grafana)

## ADR-013: ชั้นที่ 4 ของ config — ความรู้เฉพาะไซต์ที่ระบบถามสะสมเอง (ask-when-unsure)
- **ตัดสินใจ (2026-08-13):**
  1. VLM ตอบ `uncertain` + คำถามภาษาไทยได้เมื่อไม่มั่นใจ → ระบบส่งคำถามพร้อมภาพเข้า LINE แทนการแจ้งเตือนปกติ (ถามแทนเดา)
  2. คำตอบที่ผู้ใช้พิมพ์กลับใน LINE ถูกบันทึกเป็นแถวในตาราง `site_knowledge` (ต่อไซต์/ต่อกล้อง) — ความรู้เป็นข้อมูล ดู/แก้/ลบได้ในแท็บ 🧠 ของหน้าตั้งค่า ตามหลัก ADR-011
  3. ความรู้ทั้งหมดแนบเข้า VLM prompt เป็นชั้นที่ 4 ทุกครั้ง → ระบบฉลาดขึ้นเฉพาะไซต์นั้นเรื่อย ๆ ("แมวส้มบ้านนี้เดินรั้วเป็นปกติ")
  4. สถานะรอคำตอบเก็บใน `pending_questions` ผูกกับ LINE chat id — คำตอบล่าสุดจับคู่คำถามค้างล่าสุด (หน้าต่าง 48 ชม.)
- **เหตุผล:** นี่คือ moat: ระบบ rule-based สอนไม่ได้ ของเรายิ่งใช้ยิ่งรู้จักไซต์ ความรู้สะสมย้ายค่ายไม่ได้ = เหตุผลต่อสัญญา; ต่อยอด ADR-008 จาก "รู้ว่าผิด" เป็น "รู้ว่าทำไม"
- **ทบทวนเมื่อ:** ความรู้ต่อไซต์เกิน ~50 ข้อ (prompt บวม) → ทำ summarization/จัดกลุ่ม

## ADR-014: ชั้นที่ 5 — ระบบสรุป "ความปกติ" ของแต่ละกล้องเองทุกวัน + feedback ป้อนกลับ prompt
- **บริบท:** ชั้น 1-4 เรียนรู้ได้เฉพาะเท่าที่คนสอน; event ปกติหลายร้อยครั้ง/วันถูกจดแต่ไม่ถูกกลั่นเป็นความเข้าใจ; ปุ่มแจ้งเท็จบันทึกแต่ไม่ป้อนกลับ AI
- **ตัดสินใจ (2026-08-17):**
  1. ตาราง `camera_baselines` (camera_id, baseline_th, sample_count, updated_at, locked) — worker ทุกวัน 05:00 กลั่นคำบรรยาย "ปกติ" 7 วันล่าสุดของกล้อง (สูงสุด 150) ด้วย Gemini text-only เป็นย่อหน้า "สิ่งที่ปกติของกล้องนี้" แล้ว upsert
  2. Baseline แนบเข้า VLM prompt เป็นชั้นที่ 5 พร้อมกติกาเดิม: ใช้ลดเสียงรบกวน ห้ามปิดรายการเฝ้าระวังเสมอ (ชั้น 1) และถ้าขัดกับภาพให้เชื่อภาพ
  3. Feedback ป้อนกลับ: คำบรรยายของ event ที่คนกด "แจ้งเท็จ" 5 รายการล่าสุดต่อกล้อง แนบเป็น "ตัวอย่างที่เคยตัดสินผิด"
  4. แสดง/แก้/ล็อกได้ในแท็บ 🧠 (locked=true = คนแก้เองแล้ว ระบบไม่เขียนทับ) — ยังคงหลัก config-as-data
- **เหตุผล:** พนักงานที่ทำงานมาหนึ่งสัปดาห์ต้องรู้เองว่า "ที่นี่ปกติคือแบบไหน" โดยไม่ต้องมีคนบอกทุกอย่าง; ทำให้แต่ละไซต์ฉลาดขึ้นแบบวัดได้และเป็น moat อัตโนมัติ
- **ทบทวนเมื่อ:** baseline ยาวเกิน ~800 ตัวอักษร (prompt บวม) หรือมีเคสที่ baseline ทำให้พลาดเหตุจริง → ลดน้ำหนัก/เพิ่มเกราะ

## ADR-015: ตัวตรวจจับวัตถุ (YOLO) บน worker เป็นด่านแรกก่อน VLM — "สมองต้องฉลาดเองไม่พึ่งกล้อง"
- **บริบท:** ทุก event ที่มีภาพถูกส่ง Gemini หมด รวมทั้ง motion จากเงา/ฝน/ต้นไม้ (สัดส่วนสูงและกิน quota); Gemini flash-lite มองข้ามคนตัวเล็ก/ไกลในกล้องมุมกว้าง; NVR บางรุ่นแยกคน/รถให้เองแต่เราจะไม่พึ่งฟีเจอร์กล้อง — ไซต์ต่อไปกล้องจะดีหรือไม่ดี ระบบต้องฉลาดพอเอง
- **ตัดสินใจ (2026-08-18):**
  1. **ตัวตรวจจับรันใน worker (Railway) ด้วย `onnxruntime-node` ล้วน TypeScript ไม่มี Python** — โมเดล ONNX โหลดตอนสตาร์ตจาก `YOLO_MODEL_URL` ลง `YOLO_MODEL_PATH` (ไม่ commit ไฟล์โมเดล) รองรับสองรูปแบบ output: YOLOX (`[1,N,85]` ต้องถอดกริดเอง) และ YOLOv8/11 (`[1,84,N]`)
  2. **โมเดลตั้งต้น = YOLOX (Apache-2.0)** ไม่ใช่ YOLOv8 เพราะน้ำหนัก YOLOv8/v5/v10 ของ Ultralytics เป็น AGPL-3.0 → ใช้เชิงพาณิชย์ต้องซื้อ Enterprise license หรือเปิดซอร์สทั้งระบบ; YOLOX ไม่มีเงื่อนไขนี้ สลับโมเดลได้ด้วย env เท่านั้น — **ผลวัดจริง 2026-08-18 (150 event ออฟฟิศ):** ไฟล์ `yolox_s.onnx` จาก release 0.1.1rc0 ให้ objectness < 0.35 กับคนตัวใหญ่ชัด ๆ (ลอง preprocessing 6 แบบแล้ว ไม่มีแบบไหนใช้ได้ — สงสัย export ผิดยุค) ส่วน `yolox_tiny.onnx` (416) ทำงานถูก จึงใช้ tiny + **tiled inference** (เต็มเฟรม + 2×2 ซ้อนขอบ 15% แล้วรวม NMS) เพื่อจับคนตัวเล็กใน sub-stream 704×480 ของ DVR; เกณฑ์ 0.3 → กรอง 20%, 260 ms/ภาพ, พลาดของจริง 1/150 (พนักงานนั่งโต๊ะ กล้องมุมสูง ระดับ info)
  3. **สามโหมดผ่าน `YOLO_MODE`:** `off` (ค่าเริ่มต้น) / `shadow` (ตรวจแล้วบันทึกลง `events.ai.detector` แต่ยังส่ง Gemini ทุกภาพเหมือนเดิม — ใช้วัดว่าจะกรองพลาดของจริงไหมก่อนเปิดจริง) / `gate` (กรองจริง)
  4. **กติกากรอง (gate):** ข้าม Gemini เฉพาะเมื่อ (ก) event เป็นประเภทที่ขึ้นกับ "คน/รถ" (person_detected, vehicle_detected, line_crossing, intrusion, loitering, unknown/motion) **และ** (ข) ตัวตรวจจับไม่พบคน/รถ/สัตว์ใหญ่เลย — ส่วน patrol, camera_offline, ควัน/ไฟ/กล้องถูกบัง (สิ่งที่ detector มองไม่เห็น) ส่ง Gemini เสมอ ภาพที่ถูกกรองบันทึกเป็น `verified=false, model="detector-gate"` ไม่แจ้ง LINE แต่ยังเห็นใน dashboard
  5. **Fail-open ต่อจาก ADR-005:** detector ล่ม/ช้าเกิน `YOLO_TIMEOUT_MS` (3 วิ)/ไม่มีโมเดล → ปล่อยผ่านไป Gemini เหมือนไม่มี detector ห้ามทิ้ง event เด็ดขาด
  6. **ช่วยตา ไม่ใช่แค่กรอง:** เมื่อพบคน/รถ ให้ crop บริเวณนั้น (ขยายขอบ) แนบเป็นภาพที่ 2 ให้ Gemini พร้อมข้อความ "ตัวตรวจจับเบื้องต้นพบ … (อาจผิดได้ ให้เชื่อภาพ)" — เพื่อลด anchoring ถ้า detector ผิด
- **ไม่ทำ (วัดแล้ว 2026-08-18):** กรองด้วย "ฉากเหมือนเดิมกับที่เพิ่งวิเคราะห์ไป ไม่ต้องถามซ้ำ" — ทดลองกับ event จริง 250 ใบ (ลายเซ็นฉาก = ชนิด+จำนวนวัตถุ, ทั้งแบบนับตรงและแบบแบ่งช่วง, จำกัดเฉพาะเวลางาน) ได้ประหยัดแค่ **9-11%** แต่**หลุดเหตุ warning ทั้งสองรอบ** รอบแรก: คนเดินกลางดึกที่ลานจอด (person:1 → person:1 คนละคนละที่) รอบสอง: พนักงานนั่งเอนหงายคล้ายหมดสติกลางออฟฟิศ (detector เห็นเป็น person:7+ เหมือนเดิมเป๊ะ) — **บทเรียนเชิงหลักการ: detector บอกได้แค่ "มีอะไรอยู่" บอกไม่ได้ว่า "ผิดปกติไหม" สิ่งที่ทำให้เหตุการณ์น่าสงสัยคือท่าทาง/บริบท ซึ่งมองไม่เห็นในระดับกล่องวัตถุ** ทุกกฎตระกูล "เหมือนเดิม = ข้าม" จึงแลกความปลอดภัยกับค่าใช้จ่ายเสมอ ห้ามใช้กับรายการเฝ้าระวังชั้น 1
- **ไม่ทำ:** pose/โครงกระดูก — ช่วยเฉพาะเคส "คนล้ม" ซึ่งต้องดูหลายเฟรมต่อเนื่อง เหมาะกับโหมดกล่อง Edge (ADR-001) ค่อยพิจารณาเมื่อมี stream
- **เหตุผล:** ประหยัด Gemini ครึ่งหนึ่งขึ้นไปในกล้อง motion ทั่วไป, แม่นขึ้นกับคนตัวเล็ก, และความฉลาดอยู่ที่เราไม่ใช่ที่กล้องลูกค้า (ย้ายไซต์ได้โดยไม่ต้องหวังฟีเจอร์ NVR)
- **ทบทวนเมื่อ:** shadow mode พบว่ากรองพลาดเหตุจริง > 1% หรือ CPU ของ Railway ไม่พอ (ย้าย detector ไป bridge PC/กล่อง Edge) หรือมี ONNX เบากว่าที่ license เปิด
